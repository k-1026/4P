## 1. 우리 프로젝트에 각 AI 에이전트를 만들려면 어떤 API를 가져와야 하나?

**질문**

> https://github.com/k-1026/4P/tree/main/%ED%98%BC%EB%B0%A5
> 우리 팀의 프로젝트를 너가 파악하고, 우리 프로젝트에 각 ai에이전트를 만들어야하는데 어떤식으로 어떤 api를 가져와야하는지 쉽게 설명해
>
> [이미지: 오케스트레이터 아래 탐색·혼밥 분석·상황·검증 에이전트 4개, 각각의 도구(장소 검색 API, 리뷰 검색, 날씨·길찾기, 규칙 체크리스트), 맨 아래 공유 상태(작업 보드)가 있는 구조도]

**답변**

### 우리 프로젝트 요약

- **대구 혼밥 식당 챗봇**이고, 페르소나는 점심에 혼자 먹을 곳을 찾는 달서구 32세 직장인입니다.
- 핵심은 **1인분이 되는 식당만 골라 보여 주기**(기회 O2)입니다.
- 지금 챗봇은 HTML 파일 하나로 돌아갑니다. 규칙이 먼저 조건을 알아듣고, 규칙이 못 알아들은 문장만 Gemini에 보냅니다. 식당 5,498곳 데이터가 파일 안에 들어 있습니다.
- 팀 원칙: **"식당 이름과 1인분 판정은 항상 팀 데이터에서만 나온다."** 에이전트를 만들어도 이 원칙은 지켜야 합니다.

### 먼저 알아 둘 것

**에이전트마다 AI API를 따로 살 필요가 없습니다.** 보라색 칸 5개는 모두 같은 Gemini 키 하나로 만듭니다. 칸마다 다른 건 두 가지뿐입니다.
1. 시스템 프롬프트(역할 설명)
2. 쓸 수 있는 도구(회색 칸): Gemini의 function calling으로 연결

**에이전트 = Gemini(머리) + 도구 API(손)** 이고, 따로 받아야 하는 건 회색 칸의 도구 API입니다.

### 칸별로 필요한 API

| 에이전트 | 하는 일 | 가져올 API | 비고 |
|---|---|---|---|
| 오케스트레이터 | 계획, 일 나눠 주기, 반려되면 다시 계획 | Gemini API | 다른 에이전트를 부르는 역할 |
| 탐색 | 후보 가게 모으기 | ① 팀 데이터 5,498곳 ② 카카오 로컬 API ③ 소상공인 상가(상권)정보 API | 카카오는 최대 45곳. 위치·이름 확인에만 쓰고 1인분 판정은 팀 데이터 |
| 혼밥 분석 | 혼밥 지수 내기 | ① 팀 1인분 판정 데이터 ② 네이버 검색 API(블로그) 또는 카카오 블로그 검색 API | 지도 리뷰는 공식 API가 없음. 크롤링은 약관 위반 |
| 상황 | 영업시간·날씨·동선 | 기상청 단기예보 API, TMAP 보행자 경로 API, 대구푸드 맛집 DB(영업시간) | 카카오·네이버 길찾기는 자동차 길만 줌 |
| 검증 | 조건 위반 점검 | 필요 없음. 팀 판정 규칙을 코드 체크리스트로 | if문이 AI보다 정확. 걸리면 반려 사유를 오케스트레이터로 |
| 공유 상태 | 후보·근거·반려 사유 저장 | 필요 없음. JSON 객체 하나 | 여러 사용자가 쓰게 되면 Firebase나 Supabase |

### 11-27까지 실제로 받을 키 (최소)

1. Gemini API 키 (이미 있음)
2. 카카오 디벨로퍼스 REST API 키 (로컬과 블로그 검색이 키 하나로 됨)
3. 공공데이터포털 기상청 단기예보 키 (무료, 승인까지 1~2시간)

### 주의할 점

- 지금 챗봇은 브라우저 HTML 하나라서 키를 넣으면 누구나 볼 수 있습니다. 공개하려면 키를 숨길 작은 서버가 필요합니다.
- 메뉴판 사진 읽기(O1)는 약관 확인 전이므로 이번 범위에서 뺍니다.

정리하면 AI는 Gemini 하나, 도구는 카카오 + 기상청 두 개면 구조를 그대로 만들 수 있습니다.

## 3. 탐색 에이전트를 만들기 위해 해야 할 것을 쉽게 계획해 줘

**질문**

> 나는 탐색 에이전트 만드는 역할을 맡았어. 사용자가 요청을 하면 오케스트레이터가 각 서브에이전트에게 역할을 배분해. 오케스트레이터와 탐색 에이전트는 가게 데이터를 갖고 있고, 사용자가 탐색 에이전트 안에 이미 존재하는 가게를 물어보면 탐색 단계를 뛰어넘고 바로 혼밥분석→상황→검증→오케스트레이터(최종결론)로 가는 식이야. 탐색 에이전트를 만들기 위해 해야 할 것을 쉽게 계획을 세워줘

**답변**

### 먼저 짚을 점: 건너뛰는 건 "검색"뿐

가게 이름으로 바로 가도 좌표 붙이기는 해야 합니다. 좌표가 없으면 상황 에이전트가 "걸어서 몇 분"을 계산하지 못합니다.

```
사용자 말
  └ 오케스트레이터: 가게 이름이 들어 있나?
       ├ 있음 → [바로 넣기]  그 가게 + 좌표만 넣음  (검색 건너뜀)
       └ 없음 → [조건 검색]  조건으로 후보 30곳 + 좌표
                     ↓
           혼밥 분석 → 상황 → 검증 → 오케스트레이터 종합
```

### 계획

1. **주고받는 모양 정하기**: 받는 것(조건 또는 가게 이름), 주는 것(`board.candidates`)
2. **가게 이름 찾기 기능**: 띄어쓰기·지점명·괄호를 없애고 비교. `가게잇기_규칙.md` 활용. 같은 이름이 여러 곳이면 구로 좁히고, 그래도 여러 곳이면 되묻기
3. **바로 넣기 기능**: 찾은 가게 1곳 + 카카오 좌표. 이름으로 물어본 가게는 2인분 이상이어도 빼지 않고 검증에서 알려 줌
4. **조건 검색 다듬기**: 가격 모르는 가게 처리, 정렬, 카카오 결과가 진짜 그 가게인지 주소로 확인
5. **오케스트레이터 담당과 맞출 것**: 바로 넣기에서 반려되면 재계획 대신 이유를 알려 줌 / 데이터에 없는 가게를 물으면 어떻게 할지 팀이 결정
6. **시험 문장**: 정확한 이름, 지점 여러 곳, 띄어쓰기 다름, 2인분 이상 가게, 없는 가게, 조건 문장

추천 순서: 2 → 3 → 6 → 4 → 5

## 4. 팀 데이터 + 카카오 로컬 + 상가정보 API로 "~~가게 혼밥 가능해?"에 후보 가게만 모으는 에이전트를 만들 거야. 예상되는 문제점과 계획을 알려 줘

**답변**

### 예상되는 문제점

1. **상가정보 API로는 가게 이름 검색이 안 됨** (동·반경·업종 단위로 목록을 통째로 줌)
2. **사용자가 이름을 정확히 말하지 않음** ("한씨네 추어탕", "추어탕집"은 이름이 아님)
3. **같은 이름 가게가 여러 곳** (지점, 대구 밖)
4. **세 출처의 정보가 서로 다름** → 상호 + 주소로 맞춤 (`가게잇기_규칙.md`)
5. **팀 데이터에 없는 가게는 1인분 여부를 모름** → 지어내지 말고 "1인분 확인 안 됨"
6. **폐업한 가게가 섞임** → 카카오로 지금 있는지 확인
7. **카카오 키워드 검색은 최대 45곳**, 하루 한도 있음
8. **카카오 결과를 DB로 쌓는 건 약관 확인 필요**

### 만드는 순서

1. 준비: 카카오 REST 키, 공공데이터포털 상가정보
2. 문장에서 가게 이름 꺼내기 (안 되면 Gemini)
3. 팀 데이터에서 찾기 (1순위)
4. 카카오로 확인 (대구 주소만, 좌표·주소)
5. 상가정보로 보충 (둘 다 못 찾을 때만)
6. 합치고 결과 정하기 (1곳 / 여러 곳 되묻기 / 못 찾음)
7. 보드에 넣기 (탐색은 모으기만)
8. 시험하기

## 5. "상가정보 API로는 이름 검색이 안 된다"는 문제는 이미 가게 데이터가 있으면 문제가 안 되는 거지?

**답변**

거의 맞습니다. 다만 **팀 데이터에 있는 가게에 대해서만** 맞습니다.

- **팀 데이터에 있는 가게**: 팀 데이터에서 이름으로 바로 찾으면 되므로 상가정보는 필요 없음
- **팀 데이터에 없는 가게**: 5,498곳은 대구 음식점 전체(수만 곳)의 일부라 자주 생김. 이때 상가정보로 찾으려면 문제 1이 다시 생김
- 그런데 상가정보에서 찾아도 얻는 건 **업종과 주소뿐**. "있는 가게인지 + 위치"는 카카오가 더 최신이고 이름 검색도 됨

**추천**: "~가게 혼밥 가능해?" 질문에는 상가정보 API를 빼도 됨. 출처가 **팀 데이터 + 카카오** 두 개로 줄어 더 쉬워짐.

## 6. 팀 데이터에 없는 가게는 위 API나 데이터로도 못 찾는다는 거지? 그렇다면 다른 API나 대체방안을 찾아줘

**답변**

아니요, **찾을 수 있습니다.** "가게를 찾는 것"과 "1인분 여부를 아는 것"은 다른 문제입니다.

| | 팀 데이터에 있는 가게 | 팀 데이터에 없는 가게 |
|---|---|---|
| 가게 찾기 | 팀 데이터 | **카카오 로컬 API로 찾을 수 있음** |
| 1인분 되는지 | 팀 판정 있음 | 모름 |

탐색 에이전트에서 막히는 부분은 없고, 팀 데이터에 없는 가게는 "1인분 확인 안 됨"으로 넘기면 됩니다.

### 더 쓸 수 있는 API

| API | 장점 | 한계 |
|---|---|---|
| 카카오 로컬 (주력) | 이름 검색, 좌표, 업종, 무료 | 최대 45곳 |
| 네이버 검색 API: 지역 | 카카오 보조 | 최대 5곳, 좌표 변환 필요 |
| 지방행정 인허가 데이터 (일반음식점) | 공식 자료, 폐업 여부 | 파일로 받아 비교 |
| Google Places API | 영업시간, 리뷰 | 유료, 동네 식당 정보 적음 |

추천: ① 팀 데이터 → ② 카카오 로컬 → ③ 네이버 지역 검색(보조) → (선택) 인허가 데이터

## 7. 내 에이전트는 1인분 여부를 알 필요가 없고, 팀 데이터에 있으면 채택, 없으면 탐색 에이전트가 찾아주는 거야

**답변**

```
"○○가게 혼밥 가능해?"
  → 오케스트레이터: 팀 데이터에 ○○가게가 있나?
       ├ 있음 → 그 가게를 채택 (탐색 안 거침)
       └ 없음 → 탐색 에이전트(내 담당)가 카카오 등으로 찾아 줌
  → 혼밥 분석 → 상황 → 검증 → 오케스트레이터 종합
```

내 탐색 에이전트의 일은 **"팀 데이터에 없는 가게를 외부 API로 찾아, 다음 에이전트가 쓸 수 있는 모양으로 넘기기"** 하나입니다.

**생길 문제**: 사용자가 "한씨네 추어탕"이라고 하면 팀 데이터의 "한씨네대가추어탕"을 오케스트레이터가 못 찾고 탐색으로 넘길 수 있음 → 탐색이 카카오에서 찾은 **상호 + 주소로 팀 데이터를 한 번 더 확인**해서 해결.

**바뀐 계획**
1. 받는 것(가게 이름 + 동네)과 주는 것(이름·주소·구·업종·좌표·지도 링크·출처) 정하기
2. 카카오로 찾기 (대구 주소, 음식점만)
3. 못 찾으면 네이버 지역 검색으로 한 번 더
4. 팀 데이터와 다시 맞춰 보기
5. 결과 정리 (1곳 / 여러 곳 되묻기 / 0곳 못 찾음)
6. 시험하기

필요한 키: 카카오 REST API 키 하나면 시작 가능.

## 8. 이게 REST API 키인데, 이건 지도 API 아니야?

**질문**

> [이미지: 카카오 디벨로퍼스 앱 "지도"의 플랫폼 키 화면 — REST API 키, JavaScript 키]

**답변**

아니요, 지도 전용 키가 아닙니다. 탐색 에이전트에 필요한 키가 바로 이 키입니다 (직접 호출해서 확인함).

- 맨 위 **"지도"는 앱 이름**일 뿐, 키 종류가 아님
- **REST API 키**: 서버·파이썬에서 부르는 로컬(장소 검색)·블로그 검색 등 → **탐색 에이전트에 쓸 키**
- **JavaScript 키**: 웹 화면에 지도를 직접 그릴 때

확인 결과: "대구 한씨네대가추어탕" 검색 → "한씨네대가추어탕 종로점", 주소(대구 중구 약령길 51), 좌표, 업종, 카카오맵 링크가 나옴. 블로그 검색도 됨.

**키 관리**: 팀 저장소는 공개 저장소라 코드나 커밋에 키를 넣으면 안 됨. `.env`에 넣으면 올라가지 않음. 공개됐다면 새 키를 만들고 이전 키를 지울 것.

## 11. 1번 잘 이해가 안 돼

**답변**

`.env` = **프로그램 전용 비밀 메모지**입니다. 키를 코드에 바로 적으면 GitHub에 올릴 때 같이 공개되므로, 따로 된 메모지에 적어 두고 프로그램이 실행될 때 꺼내 씁니다. 이 메모지는 GitHub에 올라가지 않게 막아 두었습니다.

→ `.env` 파일을 대신 만들어 카카오 키를 넣고, 프로그램이 키를 읽는 것까지 확인했습니다.

## 12. 만들어 줘 (탐색 에이전트)

**답변**

탐색 에이전트를 만들고 실제 카카오 API로 시험까지 했습니다.

| 파일 | 내용 |
|---|---|
| `agents/explore.py` | 내 탐색 에이전트. `find_store`: 팀 데이터에 없는 가게를 카카오(없으면 네이버)에서 찾음 |
| `store_lookup.py` | 가게 이름 꺼내기, 팀 데이터에서 찾기, 지도 가게를 팀 가게와 잇기 (오케스트레이터와 공용) |
| `agents/orchestrator.py` | `ask_about_store` 추가: 팀 데이터에 있으면 채택, 없으면 탐색에 맡김 |

가게 잇기는 팀 문서 `가게잇기_규칙.md`대로 **상호 + 주소**로 잇고, 확실하지 않으면 잇지 않습니다.

| 질문 | 결과 |
|---|---|
| 한씨네대가추어탕 혼밥 가능해? | 팀 데이터에 있음 → 탐색 건너뜀 |
| 한씨네 추어탕 혼밥 돼? | 카카오에서 찾음 → 주소로 확인하니 팀 가게 → 팀 판정으로 답함 |
| 봉구스밥버거 경북대점 | 팀에 없음 → 카카오에서 1곳, "1인분 확인 안 됨" |
| 청밭추어탕 혼밥? | 팀에 3곳 → 되묻기 |
| 청밭추어탕 지산범물점 / 달서구 청밭추어탕 | 1곳으로 좁힘 |
| 봉구스밥버거 반월당점 | 카카오에도 없음 → 못 찾음 |
| 스타벅스 동성로점 | 음식점이 아니라 제외 |
| 추어탕집 혼밥 가능해? | 가게 이름 아님 → 조건 검색 |

고친 문제: 지점을 말해도 모든 지점이 나오던 문제, 사용자 위치를 모르는데 "걸어서 129분, 너무 멂"이 뜨던 문제, "추어탕집"이 메뉴 이름으로 쓰이던 문제.

남은 것: 네이버 보조 검색 미시험, "2번" 같은 되묻기 답 처리, 다른 담당자에게 수정 사항 공유, 팀 저장소 업로드.

## 13. 그래서 결과가 뭘로 나온 거야?

**답변**

탐색 에이전트의 결과는 **결과 종류 하나 + 후보 가게 목록**입니다. 답장 문장은 오케스트레이터가 마지막에 만듭니다.

| 값 | 뜻 | 다음 |
|---|---|---|
| `found` | 1곳 찾음 | 혼밥 분석으로 |
| `ambiguous` | 여러 곳 | 되묻기 |
| `not_found` | 대구 음식점 중에 없음 | 못 찾음 |
| `no_key` | 지도 API 키 없음 | 찾을 수 없음 |

실제 결과 ("봉구스밥버거 경북대점 혼밥 가능해?"):

```
결과 종류: found
가게 이름   봉구스밥버거 경북대점
구          북구
주소        대구 북구 대학로23길 17
좌표        경도 128.6101, 위도 35.8942
지도 링크   http://place.map.kakao.com/19533218
찾은 곳     카카오
팀 데이터   없음
1인분       모름
```

한마디로 **"이 가게가 맞고, 여기 있고, 팀 데이터에 있는지 없는지"를 정리한 가게 카드**입니다.

**답변**

## 17. 카카오 API를 넣는 게 좋은 이유

**답변**

1. **팀 데이터에 없는 가게도 찾음** (가장 큰 이유)
2. **이름으로 검색됨** (상가정보는 목록 통째)
3. **대충 말해도 잡아 줌** ("한씨네 추어탕" → 한씨네대가추어탕 종로점 → 팀 가게와 이음)
4. **다른 에이전트에 필요한 정보를 한 번에 줌** (좌표, 주소, 업종, 지도 링크)
5. **지금도 있는 가게인지 확인됨**
6. **키 하나로 여러 곳에 씀** (블로그 검색까지)

| | 카카오 로컬 | 네이버 지역 | 상가정보 | Google Places |
|---|---|---|---|---|
| 이름 검색 | ✅ | ✅ | ❌ | ✅ |
| 결과 수 | 최대 45 | 최대 5 | 목록 통째 | 여러 곳 |
| 좌표 | ✅ | 변환 필요 | ✅ | ✅ |
| 비용 | 무료 한도 | 무료 한도 | 무료 | 유료 |

한계: 영업시간·가격·메뉴 없음, 최대 45곳, 하루 한도, 결과 저장은 약관 확인 필요.

한마디로 **팀 데이터는 "혼밥 판정", 카카오는 "어디 있는 진짜 가게인지"** 를 맡습니다.

## 22. 팀 데이터에 해당하는 가게가 있으면 바로 혼밥 분석으로 넘어가고, 없으면 카카오 API를 적용한 탐색 에이전트가 작동하는 거지?

**질문**

> [이미지: 처음의 구조도]

**답변**

네, 맞습니다.

```
사용자: "○○ 혼밥 가능해?"
  → 오케스트레이터: 팀 데이터에 ○○가 있나?
       ├ 있음 (1곳)  → 탐색 건너뜀 → 바로 혼밥 분석 → 상황 → 검증
       └ 없음        → 탐색 에이전트 (카카오 장소 검색 API)
                         → 찾으면 혼밥 분석 → 상황 → 검증
```

그림의 "탐색 → 장소 검색 API" 줄은 팀 데이터에 없을 때만 실행됩니다. 팀 데이터를 확인하는 일은 탐색이 아니라 오케스트레이터가 합니다.

알아 둘 것: 팀 데이터에 같은 이름이 여러 곳이면 먼저 되묻기 / 탐색이 카카오에서 찾았는데 사실 팀 가게면 팀 판정으로 넘김 / (당시) 혼밥 관련 질문만 이 흐름을 탐.

## 23. "혼밥 가능해?"에 너무 치중되어 있어. 다른 질문을 할 경우 예시와 탐색 에이전트에서 어떻게 작동하는지

**답변**

어떤 질문을 해도 가게 이름을 알아채도록 고쳤습니다 (실제 카카오 검색으로 확인).

**핵심: 탐색 에이전트가 하는 일은 질문 종류와 상관없이 같습니다.** "몇 시까지 해?"든 "메뉴 뭐 있어?"든 그 가게를 찾아 가게 카드로 넘길 뿐이고, 질문 종류는 오케스트레이터가 기록해 다음 에이전트가 답을 정할 때 씁니다.

```
질문 → 오케스트레이터: ① 가게 이름 꺼내기  ② 질문 종류 알아내기
     → 팀 데이터에 있나?
          ├ 있음 → 탐색 건너뜀
          └ 없음 → 탐색 에이전트: 카카오에서 찾기 (질문 종류와 무관하게 똑같이)
     → 다음 에이전트: 질문 종류에 맞게 답을 만듦
```

| 사용자 질문 | 꺼낸 가게 | 질문 종류 | 탐색 에이전트 | 넘기는 것 |
|---|---|---|---|---|
| 한씨네대가추어탕 몇 시까지 해? | 한씨네대가추어탕 | 영업시간 | 건너뜀 | 팀 가게 카드 |
| 혼밥하기 좋은 한씨네대가추어탕 | 한씨네대가추어탕 | 혼밥 여부 | 건너뜀 | 팀 가게 카드 |
| 한씨네 추어탕 맛있어? | 한씨네 추어탕 | 평가 | 카카오 1곳 → 팀 가게와 이음 | 팀 가게 카드 |
| 교동짬뽕 몇 시까지 해? | 교동짬뽕 | 영업시간 | 카카오 2곳 → 1곳 | 카카오 가게 카드 |
| 봉구스밥버거 경북대점 영업해? | 봉구스밥버거 경북대점 | 영업시간 | 카카오 1곳 | 카카오 가게 카드 |
| 을지로골뱅이 메뉴 뭐 있어? | 을지로골뱅이 | 가격·메뉴 | 카카오 3곳 | 되묻기 |
| 청밭추어탕 주차 돼? | 청밭추어탕 | 위치 | 건너뜀 (팀에 3곳) | 되묻기 |
| 동성로 혼밥 맛집 추천해줘 | 없음 | 혼밥 여부 | 안 씀 | 조건 검색 |
| 점심 뭐 먹지? | 없음 | 모름 | 안 씀 | 조건 검색 |

바뀐 것:
- `store_lookup.detect_store`: 문장 안에 팀 가게 이름이 있으면 위치와 상관없이 잡고, 없으면 질문 낱말 앞의 말을 이름으로 봄. 조건 말("추천·맛집·만원·10분")이나 "점심·날씨"만 있으면 가게 질문 아님
- 질문 종류 5가지: 혼밥 여부 · 영업시간 · 위치 · 가격·메뉴 · 평가 (보드에 `intent`로 남김)
- 사이트에 질문 종류 표시, 예시 3개 추가

남은 한계: 다음 에이전트는 질문 종류와 상관없이 똑같이 돎(오케스트레이터 담당과 맞출 부분) / 영업시간·가격 정보 부족 / 낯선 말투는 놓칠 수 있음(Gemini로 보완 가능).

## 24. 옆에 한씨네대가추어탕, 봉구스밥버거 같은 건 예시인 거야?

**답변**

네, 입력창 아래 버튼들은 **눌러 보라고 넣은 예시 질문**입니다. 가게는 지어낸 것이 아니라 **실제 대구 가게**이고, 각 경우가 한 번씩 보이도록 골랐습니다.

| 예시 버튼 | 보여 주려는 경우 |
|---|---|
| 한씨네대가추어탕 혼밥 가능해? | 팀 데이터에 있음 → 탐색 건너뜀 |
| 한씨네 추어탕 혼밥 돼? | 줄여 말함 → 카카오에서 찾아 팀 가게와 이음 |
| 봉구스밥버거 경북대점 혼밥 가능해? | 팀 데이터에 없음 → 카카오에서 찾음 |
| 청밭추어탕 혼밥? | 여러 곳 → 되묻기 |
| 봉구스밥버거 반월당점 혼밥 가능해? | 카카오에도 없음 → 못 찾음 |
| 추어탕집 혼밥 가능해? | 가게 이름 아님 → 조건 검색 |
| 교동짬뽕 몇 시까지 해? | 혼밥이 아닌 질문도 가게를 찾음 |
| 을지로골뱅이 메뉴 뭐 있어? | 메뉴 질문 + 여러 곳 → 되묻기 |
| 혼밥하기 좋은 한씨네대가추어탕 | 이름이 문장 뒤에 와도 찾음 |

입력창에 아무 질문이나 직접 써서 "찾기"를 눌러도 됩니다.

## 25. 팀 데이터에 없는 가게면 어떤 요청이든 탐색 에이전트가 작동하는 거지? 그 툴을 내가 만든 거지?

**답변**

### 팀 데이터에 없는 가게면 작동하나?

네. 조건은 **문장에서 가게 이름을 알아채야** 한다는 것 하나입니다.

| 경우 | 탐색 에이전트 |
|---|---|
| 가게 이름 있음 + 팀 데이터에 없음 | ✅ 작동 (어떤 질문이든) |
| 가게 이름 있음 + 팀 데이터에 있음 | 건너뜀 |
| 가게 이름 없음 ("추천해줘", "점심 뭐 먹지?") | 작동 안 함 → 조건 검색 |

### 그 툴을 내가 만든 건가?

- **장소 검색 API(도구)** 는 **카카오가 만든 것**이고, 키를 받아 가져다 씀 (그림의 회색 칸)
- **탐색 에이전트**(그림의 보라색 칸)가 **내 담당**: 카카오 API를 언제 어떻게 부를지, 어떻게 거르고 팀 데이터와 잇고 무엇을 넘길지를 정한 부분
- **흐름과 요구사항은 내가 정했고, 코드는 이 대화에서 Claude가 작성했습니다.**

팀에 설명하려면 이해해 둘 파일:

| 파일 | 내용 |
|---|---|
| `agents/explore.py` | 탐색 에이전트 본체 (`find_store`) |
| `store_lookup.py` | 가게 이름 꺼내기, 팀 데이터와 잇기 |
| `tools.py`의 `kakao_search` | 카카오 장소 검색 API 호출 |
| `server.py`, `web/index.html` | 시연용 사이트 |

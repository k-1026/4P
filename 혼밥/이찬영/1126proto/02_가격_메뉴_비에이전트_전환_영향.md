# 가격·메뉴를 에이전트에서 빼면 — 바뀌는 데이터와 끊기는 흐름

- 작성일: 2026-11-27
- 전제(사용자 방향): 가격과 메뉴는 정량값이라 에이전트(LLM)로 설계하지 않는다.
- 이 문서는 그 결정으로 **바뀌는 데이터·값**과 **논리적 흐름이 끊기는 곳**을 정리한다.
  설계 문서·코드는 아직 고치지 않았다(6절에 고칠 곳).
- 기준 문서: `00_전체구조.md`, `criteria.json`, `scoring.py`, `prompts/*.md`, 실제 웹앱 <https://honbap-bapchingu.vercel.app> (2026-11-26 확인)

## 1. "에이전트가 아니다"의 뜻

| 구분 | 에이전트일 때 | 에이전트가 아닐 때 |
|---|---|---|
| 값을 내는 방법 | LLM이 판단하고 도구를 부름 | 코드(`scoring.py`)와 미리 계산한 데이터만 씀. 같은 입력이면 늘 같은 값 |
| 말하기 | 첫 의견, 상의 때 반론·설득 | 없음 |
| 실패 | `status: fail` → 조율자가 빼고 가중치 재배분 | 데이터가 없으면 그 가게만 `unknown` |
| 재계획 | 검증이 반려하면 다시 호출 | 다시 돌려도 같은 값 → 재계획 대상이 아님 |

- 그래서 구조는 **조율자 + 서브 에이전트 4개(날씨 · 취향기록 · 거리 · 혼밥편의) + 검증**이 된다.
- 피칭 PDF 9쪽("오케스트레이터 하나, 서브에이전트 다섯": 날씨·취향기록·거리·혼밥편의·검증)과 이미 같은 구조다.
  지금 어긋난 것은 `00_전체구조.md`(에이전트 8개)와 실제 앱(쫀득이·가격, 폭신이·메뉴가 말함) 쪽이다.

## 2. 그대로인 것

- 예산 **점수 식**: 후보끼리 상대 비교 `floor(10 × 더 비싼 가게 수 ÷ (n − 1) + 0.5)`, 상한 초과 drop, 5곳 미만이면 절대 규칙.
  이미 `scoring.score_budget`이 계산하고 있어 숫자는 바뀌지 않는다.
- segment와 상한: 혼밥 MBTI V → 1만 원, P → 상한 없음, 없음 → 1.3만 원, 사용자가 말한 예산이 우선.
  조율자가 정하던 것이라 그대로다.
- 가중치 숫자: 예산 20%(기본)는 "점수 항목"으로 그대로 남는다.
  메뉴는 원래 0%라 점수에 영향이 없다.
- 혼밥·거리·날씨·취향 점수 식.

## 3. 바뀌는 데이터·값

| 값 | 지금 누가 만드나 | 바뀐 뒤 | 지금 데이터 상태 |
|---|---|---|---|
| 1인 메뉴 목록 | 메뉴 에이전트가 이름에 "2인"이 있으면 뺌 | DB를 만들 때 이미 1인분 근거만 넣음 → `data/메뉴.json` 그대로 | ✅ 391곳 · 1,056개 |
| 1인 가격 (`price`) | 메뉴 에이전트가 가격 목록을 붙이고, 예산 에이전트가 중앙값 | `메뉴.json` 가격의 중앙값을 미리 계산해 가게 데이터에 붙임 | ✅ 1인 메뉴 근거 가격 380곳 · 주요메뉴 단품까지 388곳 · 3곳 없음 |
| 음식 종류 (`kind`, 11가지) | 메뉴 에이전트가 메뉴 이름·업종을 보고 판단 | 낱말 규칙 + **업종 → 11가지 대응표** | ⚠️ 대응표 없음(D12). 대표 메뉴 낱말 규칙만으로는 **95곳(24%) 모름** |
| 날씨용 종류 (`weather_type`) | 메뉴 에이전트가 판단 | 낱말 규칙 (냉면·물회 → 차가운 요리, 국물 → 따뜻한 국물, 나머지 → 따뜻한 요리) | ⚠️ 규칙만으로 93곳 모름 |
| 국물 여부 (`soup`) | 메뉴 에이전트가 판단 | 낱말 규칙 또는 수작업 | ❌ `메뉴.json` 1,056개 모두 비어 있음 |
| 예산 점수·판정 | 예산 에이전트가 `score_budget`을 부름 | 조율자가 `score_budget`을 직접 부름 | ✅ 같은 값 |
| 예산 확실도 (`confidence`) | 예산 에이전트가 판단 (메뉴판·12개월 기준) | **규칙으로 정해야 함**: 사람확인 → high, 검토전 → mid, 가격 없음 → low | ⚠️ 규칙이 `criteria.json`에 없음 |
| 가격 VOC 분류 (긍정·부정) | 예산 에이전트(LLM)가 문장 분류 | 할 수 없음 (규칙으로 대신하거나 버림) | 이미 꺼져 있음 (`voc_enabled: false`) |
| 첫 의견·반론 문장 | 예산·메뉴 에이전트가 말함 | 없음, 또는 조율자가 정해진 문장 틀로 사실만 말함 | – |
| `status: partial` (가격 아는 가게 5곳 미만) | 예산 에이전트가 알림 | 도구 결과의 표시값(`how`)으로 남음 | ✅ `score_budget`이 이미 "절대 규칙" 문구를 냄 |

- 음식 종류 숫자는 대표 메뉴 이름 하나에 간단한 낱말 규칙을 댄 **어림값**이다(2026-11-27, `메뉴.json` 기준).
  업종 대응표를 붙이면 줄어든다.

## 4. 끊기는 흐름

`00_전체구조.md` 6장 흐름 [0]~[9]과 프롬프트 기준이다.

### 4.1 가장 큰 두 곳

- **B2 (음식 종류·날씨용 종류):** 메뉴 에이전트가 하던 일 중 진짜 "판단"이 필요한 것은 이것뿐이다.
  미리 계산하려면 업종 26종 → 음식 종류 11가지 대응표(D12)가 꼭 있어야 한다.
- **B4 (검증 R4 반려):** 지금 규칙대로면 반려를 고칠 길이 없다.
  실제 앱처럼 예산 상한을 **후보 필터**로 옮기면 R4는 "필터가 제대로 걸렸는지 확인"만 하게 된다.

## 5. 바뀐 뒤 흐름 (제안)

```text
[0] 요청 수신 ─ 조율자: context, segment, budget_max
      │
[1] 데이터 준비 (코드) ─ 가게마다 1인 가격 중앙값 · kind · weather_type · 확실도   ← 메뉴 에이전트 대신
      │
[2] 날씨 ∥ 취향기록 ─ 첫 의견
      │
[3] 거리 ─ 1km 안 가까운 20곳  (예산 상한 넘는 가게는 여기서 뺌)   ← B4 가안
      │
[4] 혼밥편의 ∥ 거리 ∥ 취향 ∥ 날씨 ─ 점수 (에이전트)
    예산 ─ score_budget (코드)
      │
[5] 조율자 ─ 가중합 → 1·2위 차이 ≤ 0.5면 상의 (가격은 사실로만 보여 줌 ← B3 가안)
      │
[6] 검증 R1~R8 ─ reject면 날씨·취향·거리·혼밥편의만 재계획
```

# 혼밥 식당 추천 멀티 에이전트 · 전체 구조 (v2 초안 — 가격·메뉴 코드화)

> **v2 초안 (2026-11-27, 팀 결정 전 예측본).** 가격·메뉴는 정량값이라 에이전트로 두지 않고 코드가 계산한다.
> 바뀐 이유와 끊긴 흐름은 `../02_가격_메뉴_비에이전트_전환_영향.md`(B1~B11), 원본은 `../00_전체구조.md`.

이 문서는 날씨·거리·취향·혼밥편의 에이전트와 조율자·검증 에이전트, 그리고 예산·메뉴 **코드 단계**를 하나로 합친 기준 문서다.
`1123실습/예산에이전트_설계.md`의 공통 계약을 뼈대로 쓰고, `honbap/weather-agent/`에 있던 에이전트 규칙을 그 계약에 맞춰 옮겼다.
모든 판정·규칙 점수는 **10점 만점**이다.

## 1. 구조

```text
                         사용자
                           │ 요청 / ▲ 최종 답
                           ▼
   [코드] 데이터 준비 (prepare.py) ─ 1인 가격 · 음식 종류 · 날씨용 종류 · 가격 확실도
                           │ (가게마다 미리 계산)
              ┌──────────── 조율자 ────────────┐
              │ 계획 · 배분 · 가중합 · 재계획   │◀──── 반려 시 재계획 ────┐
              │ [코드] 예산 거르기 · 예산 점수 │                          │
              └───────────────────────────────┘                          │
        ┌────────┬────────┬────────┬────────┬────────┐                   │
        ▼        ▼        ▼        ▼        ▼        ▼                   │
       날씨    취향기록    거리   혼밥편의    검증 ──────────────────────┘
        │        │        │        │        │
      기상청   혼밥일기  위치·도보 1인분·좌석 판정 기준표
       API     MBTI

        ════════════ 공유 상태 (작업 보드) ════════════
        요청 · 사용자 성향 · 후보 20곳(미리 계산한 값 포함) · 에이전트 결과 · 예산 점수 · 반론 · 반려 사유
```

| 에이전트 | 영문 이름 | 하는 일 | 하지 않는 일 | 프롬프트 |
|---|---|---|---|---|
| 조율자 | coordinator | 계획, 배분, 가중치, 가중합, 상의 진행, 최종 답 | 개별 점수 계산 | `prompts/coordinator.md` |
| 날씨 | weather | 체감온도로 음식 방향, 날씨 점수 | 취향·가격 판단 | `prompts/weather.md` |
| 취향기록 | preference | 혼밥일기 별점·후기, 최근 식사, 탐험/단골 | 날씨 판단 | `prompts/preference.md` |
| 거리 | distance | 위치 파악, 가까운 20곳, 도보 시간, 거리 점수 | 가격·좌석 판단 | `prompts/distance.md` |
| 혼밥편의 | solo | 혼밥후기 순위·1인석으로 혼밥 점수 | 가격 판단 | `prompts/solo.md` |
| 검증 | verifier | 판정 기준표로 승인·반려 | 점수 수정 | `prompts/verifier.md` |

| 코드 단계 | 함수 | 하는 일 | 하지 않는 일 | 설명서 |
|---|---|---|---|---|
| 데이터 준비 | `prepare.py` | 1인 가격 중앙값, 음식 종류, 날씨용 종류, 국물 여부, 가격 확실도를 가게마다 미리 계산 | 판단·말하기 | `도구설명/데이터_준비.md` |
| 예산 | `scoring.budget_prefilter`, `score_budget`, `price_facts` | 후보 전 예산 거르기, 후보끼리 가격 상대 점수, 상의 때 가격 사실 | 말하기·반론·재계획 | `도구설명/예산_점수.md` |

- 코드 단계는 같은 입력이면 늘 같은 값을 낸다.
  그래서 첫 의견·반론·재계획이 없다.

## 2. 10점 만점 공통 규칙

모든 숫자는 `criteria.json` 한 파일에 있다.
기준을 바꿀 때는 그 파일만 고친다.

| 항목 | 규칙 |
|---|---|
| 개별 점수 | 0~10 정수. 소수는 쓰지 않는다. |
| 반올림 | 사사오입, `floor(x + 0.5)` |
| 총점 | `Σ(점수 × 가중치) ÷ 100`, 0.0~10.0, 소수 첫째 자리 |
| 탈락 | `score: null`, `verdict: "drop"` |
| 판단 불가 | `score: null`, `verdict: "unknown"`, `confidence: "low"`. 탈락이 아니다. 조율자는 그 항목을 0점으로 센다. |
| 점수 차이 말하기 | 2점 이하는 "차이가 작다", 3점 이상은 숫자로 입장을 밝힌다. |
| 별점 | 앱 별점(1~5)은 들어올 때 ×2 해서 10점으로 바꾼다 (2~10). |
| 가중치 | 퍼센트, 합계 100 (점수가 아니다) |
| 상의 | 1·2위 총점 차이 0.5점(10점 만점 기준) 이하일 때만 연다. |

### 2.1 에이전트별 점수 한눈에 보기

| 에이전트 | 10점 | 중간 | 0점 쪽 | 탈락 | 판단 불가 |
|---|---|---|---|---|---|
| 날씨 | 날씨 방향과 맞음 | 5 (애매·상관없음) | 0 (반대) | 없음 | 음식 종류 모름 |
| 거리 | 후보 중 가장 가까움 | 1분 멀어질 때마다 −1 (급하면 −2) | 0 | 도보 15분 초과 | 도보 시간 모름 |
| 예산 (코드) | 후보 중 가장 쌈 | 상대 위치 | 가장 비쌈 | 상한 초과는 후보 전에 뺌 | 가격 없음 |
| 취향 | 별점 기록 높음 + MBTI 보정 | 기록 없음 6 | 연속 식사 감점 | 없음 | 없음 (기록 없음은 6) |
| 혼밥편의 | 후보 중 혼밥후기 상위 칸 8 + 1인석 2 | 후기 순위 8칸(8~1) | 1 (꼴찌 칸, 1인석 없음) | 2인분부터 | 혼밥 DB에 없는 가게 |

## 3. 공통 계약

### 3.1 공통 입력 (조율자 → 에이전트 지시서)

```json
{
  "task_id": "req-20261126-001",
  "round": 1,
  "instruction": "후보 20곳의 날씨 점수를 매겨라.",
  "user_profile": {
    "mbti": "WBNV",
    "mbti_pct": {"W": 0.75, "B": 0.88, "N": 0.6, "V": 0.7},
    "segment": "value",
    "budget_max": 10000
  },
  "candidates": [
    {"store_id": "MA010120220800148431", "name": "이삭토스트대구 동성로점", "walk_min": 3,
     "kind": "빵·패스트푸드", "weather_type": "따뜻한 요리", "price": 4000, "price_confidence": "mid"}
  ],
  "criteria": {"...": "criteria.json의 해당 에이전트 부분"},
  "context": {"time_pressure": false, "party_size": 1, "now": "2026-11-26 12:10"}
}
```

- `store_id`는 혼밥팀 최종본 DB의 `식당ID`(상가정보 번호, `MA0101…`)다.
  가게 목록은 `data/stores_동성로391.json`이고, 앱 1차본 번호(1001~)는 `data/id_map_app276_to_db.json`으로 바꾼다.
- 혼밥 DB 391곳은 모두 1인분 근거와 좌표가 있다.
- `kind`, `weather_type`, `price`, `price_confidence`는 메뉴 에이전트가 아니라 `prepare.py`가 미리 계산한 값이다(`data/stores_prepared_v2.json`).

### 3.2 공통 출력 (에이전트 → 공유 상태)

```json
{
  "agent": "weather",
  "task_id": "req-20261126-001",
  "round": 1,
  "status": "ok",
  "opinion": "체감 4도예요. 따뜻한 국물 추천해요!",
  "results": [
    {"store_id": "MA010120220800148431", "verdict": "pass", "score": 5, "confidence": "high",
     "evidence": ["날씨 방향 따뜻한 국물", "음식 따뜻한 요리"], "reason": "국물은 아니지만 따뜻한 음식"}
  ],
  "notes": [],
  "needs": []
}
```

| 필드 | 값 | 의미 |
|---|---|---|
| `status` | `ok` / `partial` / `fail` | `partial`은 일부 가게를 판단하지 못함, `fail`은 준비 실패(조율자가 그 에이전트를 빼고 가중치 재배분) |
| `opinion` | 문자열 | 처음 하는 한두 문장 (없으면 빈 문자열) |
| `verdict` | `pass` / `drop` / `unknown` | 통과, 탈락, 판단 불가 |
| `score` | 0~10 정수 또는 null | |
| `confidence` | `high` / `mid` / `low` | 기존 코드의 높음/중간/낮음 |
| `needs` | 문자열 목록 | 조율자에게 요청할 것 |

- 예산 점수는 같은 `results` 모양(`store_id, verdict, score, confidence, evidence`)으로 공유 상태에 들어가고, `agent` 대신 `"source": "score_budget"`로 표시한다.

### 3.3 반론 형식 (상의 단계)

```json
{"agent": "preference", "stance": "반대", "confidence": "high",
 "message": "B 라멘집은 어제에 이어 또 면이에요. A 국밥집을 지지합니다.",
 "lower_confidence": {"store_id": "A", "to": "mid", "why": "좌석 후기가 3년 전 글"}}
```

- `stance`는 `동의` / `반대` / `판단 안 함`이다.
- 반론은 점수를 바꾸지 않는다.
  `lower_confidence`로 확실도만 낮출 수 있다.

## 4. 혼밥 MBTI가 들어가는 자리

| 글자 | 축 | 들어가는 곳 | 방식 |
|---|---|---|---|
| 1번째 W/A | 날씨파 / 입맛파 | 조율자 가중치 | 날씨 × (0.5 + W), 취향 × (1.5 − W) |
| 2번째 B/O | 아늑파 / 당당파 | 조율자 가중치 | 혼밥 × (0.5 + B). 퍼센트가 없으면 반영하지 않는다(혼밥 점수는 최종본 규칙 그대로) |
| 3번째 N/R | 탐험파 / 단골파 | 취향 점수 | 탐험파: 안 가본 곳 +3, 가본 곳 −2. 단골파: 가본 곳(8점 이상) +3, (6점 이상) +1, 안 가본 곳 −1 |
| 4번째 V/P | 가성비파 / 플렉스파 | 예산 segment (조율자 → 코드) | V → value(상한 10,000원), P → premium(예산 가중치 0, 거르지 않음), 없음 → unknown(상한 13,000원) |

같은 성향을 가중치와 점수에 두 번 반영하지 않는다.

## 5. 가중치

기준 열은 `criteria.json`의 `weights`에서 고른다.

| 항목 | 기본 | 시간 없음 | Premium | Premium + 시간 없음 |
|---|---|---|---|---|
| 혼밥편의 | 35 | 30 | 40 | 32 |
| 거리 | 20 | 35 | 25 | 40 |
| 예산 | 20 | 15 | 0 | 0 |
| 취향 | 15 | 12 | 20 | 16 |
| 날씨 | 10 | 8 | 15 | 12 |

계산 순서는 다음과 같다.

1. 기준 열을 고른다.
2. 혼밥 MBTI 퍼센트가 있으면 배수를 곱한다.
3. 준비에 실패한 에이전트를 빼고, 남은 항목끼리 합이 100이 되게 다시 나눈다.
   예산은 코드라 '실패'가 없다.
   가격을 모르는 가게는 그 가게의 예산만 unknown이다.

## 6. 흐름

```text
[미리] 데이터 준비 (코드, prepare.py) ─ 1인 가격 · 음식 종류 · 날씨용 종류 · 가격 확실도
      │
[0] 요청 수신 ─ 조율자가 context 추출 (시간 여유, 인원, 예산 언급, MBTI) → segment · budget_max
      │
[1] 날씨 ∥ 취향기록 ─ 첫 의견                          (동시)
      │
[2] 예산 거르기 (코드, budget_prefilter) ─ 1인 가격이 상한을 넘는 가게를 뺌 (가격 모름은 남김)
      │
[3] 거리 ─ 위치 파악, 1km 안 가까운 20곳 → 공유 상태
      │
[4] 혼밥편의 ∥ 거리 ∥ 취향 ∥ 날씨 ─ 20곳 점수   (동시, 에이전트)
    예산 점수 (코드, score_budget)
      │
[5] 조율자 ─ drop 제외 → 가중치 → 총점(10점 만점)
      │
[6] 1·2위 차이 ≤ 0.5? ──예──▶ 상의 (반론 1회, confidence만 변경 · 가격은 price_facts로 사실만 보여 줌)
      │아니오                         │
      ◀───────────────────────────────┘
[7] 검증 ─ R1~R8
      │
      ├─ reject ─▶ replan_targets(날씨·취향·거리·혼밥편의)만 재호출 → [5]로 (최대 2회)
      │
      └─ approve ─▶ [8] 최종 답 3곳
```

재계획이 2회를 넘으면 조율자는 승인된 부분만으로 답하고, 확인하지 못한 항목을 밝힌다.

## 7. 점수 도구

에이전트(LLM)는 점수를 직접 계산하지 않는다.
`scoring.py`의 함수를 도구로 불러 점수를 받는다.
예산은 에이전트 없이 조율자가 직접 부른다.

| 도구 | 에이전트 |
|---|---|
| `weather_direction`, `score_weather` | 날씨 |
| `walk_min`, `score_distance` | 거리 |
| `budget_prefilter`, `score_budget`, `price_facts` | 조율자 (예산 코드 단계) |
| `star10`, `score_preference` | 취향기록 |
| `score_solo` | 혼밥편의 |
| `weights_for`, `total_score`, `should_debate`, `gap_stance` | 조율자 |

`python3 test_v2.py`로 설계 문서·`data/role_check.json` 예시와 v2 코드 단계(예산 거르기, 가격 사실, 음식 종류 규칙)를 시험한다.

# 예산 에이전트 설계와 전체 구조

이 문서는 혼밥 식당 추천 멀티 에이전트에서 **예산** 에이전트를 정의한다.
다른 에이전트와 같은 입출력 계약을 쓰도록 맞췄고, 조율자와 검증 에이전트, 데이터, 판정 기준, 흐름도 함께 정리했다.

## 1. 전체 구조

```text
                         사용자
                           │ 요청 / ▲ 최종 답
                           ▼
              ┌──────────── 조율자 ────────────┐
              │ 계획 · 배분 · 가중합 · 재계획   │◀──── 반려 시 재계획 ────┐
              └───────────────────────────────┘                          │
        ┌──────────┬──────────┬──────────┬──────────┬──────────┐         │
        ▼          ▼          ▼          ▼          ▼          ▼         │
      날씨      취향기록     거리      혼밥편의     예산       검증 ───────┘
        │          │          │          │          │          │
     날씨 API   사용자 기록  위치·길찾기  좌석·VOC   가격·VOC   판정 기준표

        ════════════ 공유 상태 (작업 보드) ════════════
        요청 · 사용자 성향 · 후보 20곳 · 에이전트 결과 · 반론 · 반려 사유
```

역할 경계는 다음과 같다.

| 에이전트 | 하는 일 | 하지 않는 일 |
|---|---|---|
| 조율자 | 계획, 배분, 가중치 결정, 가중합, 상의 진행, 최종 답 | 개별 점수 계산 |
| 거리 | 사용자 위치 파악, 가까운 20곳 선정, 거리 점수 | 가격·좌석 판단 |
| 예산 | 20곳의 가격 비교, 상대 점수, 예산 초과 탈락 | 위치 파악, 1인분 가능 여부 |
| 혼밥편의 | 1인석·1인분 가능 여부, 혼밥 점수 | 가격 판단 |
| 취향기록 | 사용자 취향과 최근 식사 이력으로 점수 | 날씨 판단 |
| 날씨 | 기온·강수로 메뉴 적합도 점수 | 취향 판단 |
| 검증 | 판정 기준표로 결과를 점검하고 승인 또는 반려 | 점수 수정 |

## 2. 공통 계약

모든 작업 에이전트는 같은 형식으로 받고 같은 형식으로 낸다.
그래야 조율자와 검증 에이전트가 에이전트 종류와 상관없이 결과를 합칠 수 있다.

### 2.1 공통 점수 규칙

- 점수는 **0~10 정수**다.
  소수는 쓰지 않는다.
- 반올림은 사사오입(0.5는 올림)이다.
  `floor(x + 0.5)`로 계산한다.
- 탈락한 가게는 `score: null`, `verdict: "drop"`이다.
- 판단할 데이터가 없으면 `score: null`, `verdict: "unknown"`이다.
  `unknown`은 탈락이 아니다.

### 2.2 공통 입력 (조율자 → 에이전트 지시서)

```json
{
  "task_id": "req-20261126-001",
  "round": 1,
  "instruction": "후보 20곳의 가격을 비교해 예산 점수를 매겨라.",
  "user_profile": {
    "segment": "value",
    "budget_max": 10000
  },
  "candidates": [
    {"store_id": "S01", "name": "A 국밥집", "distance_m": 650}
  ],
  "criteria": { "...": "판정 기준표의 해당 에이전트 부분" },
  "context": { "time_pressure": false, "party_size": 1 }
}
```

### 2.3 공통 출력 (에이전트 → 공유 상태)

```json
{
  "agent": "budget",
  "task_id": "req-20261126-001",
  "round": 1,
  "status": "ok",
  "results": [
    {
      "store_id": "S01",
      "verdict": "pass",
      "score": 5,
      "confidence": "high",
      "evidence": ["1인 가격 9,000원", "20곳 중 더 비싼 곳 10곳"],
      "reason": "후보 중 중간 가격대"
    }
  ],
  "notes": [],
  "needs": []
}
```

| 필드 | 값 | 의미 |
|---|---|---|
| `status` | `ok` / `partial` / `fail` | `partial`은 일부 가게를 판단하지 못한 경우 |
| `verdict` | `pass` / `drop` / `unknown` | 통과, 탈락, 판단 불가 |
| `confidence` | `high` / `mid` / `low` | 근거의 확실도 |
| `needs` | 문자열 목록 | 조율자에게 요청할 것 (예: "S07 가격 데이터 필요") |

## 3. 예산 에이전트

### 3.1 점수 규칙

예산 점수는 **후보 20곳 안에서의 상대 위치**로 정한다.
절대 금액이 아니라 "주변 가게들보다 싼가"를 본다.

1. 가격이 확인된 가게만 비교 대상(n곳)으로 삼는다.
2. 각 가게마다 자기보다 **비싼** 가게 수를 센다.
3. 기본 점수는 `floor(10 × 비싼 가게 수 ÷ (n − 1) + 0.5)`이다.
   가장 싼 곳은 10점, 가장 비싼 곳은 0점이다.
   가격이 같으면 점수도 같다.
4. VOC 보정을 적용한다(3.2절).
   보정 후에도 0~10 범위를 벗어나지 않게 자른다.
5. `budget_max`를 넘는 가게는 점수와 상관없이 `drop`이다.
   상대 점수 계산에는 포함한다.
   그래야 상한이 바뀌어도 다른 가게의 점수가 흔들리지 않는다.
6. 가격이 없는 가게는 `unknown`, `score: null`, `confidence: low`이다.

예외 규칙은 다음과 같다.

| 상황 | 처리 |
|---|---|
| 가격 확인된 가게가 5곳 미만 | 상대 비교를 하지 않고 절대 규칙 사용: 상한의 80% 이하 10점, 상한 이하 5점. `status: partial` |
| `segment: premium` (`budget_max: null`) | 모든 가게 `pass`, 점수 10. `notes`에 "예산 변별력 없음"을 적어 조율자가 가중치를 재배분하게 함 |
| `segment: unknown` | `budget_max`를 1.3배로 완화해 탈락만 느슨하게 적용 |

### 3.2 VOC 보정

VOC는 가격 데이터를 보완하는 용도로만 쓴다.
보정 폭은 **±1점**으로 제한한다.

- 최근 12개월 리뷰에서 가격 관련 문장만 고른다.
- 각 문장을 `positive`(가성비, 양 많음, 저렴), `negative`(비쌈, 양 적음, 가격 인상), `none`으로 나눈다.
- 가격 관련 문장이 5개 이상일 때만 보정한다.
- `(긍정 − 부정) ÷ (긍정 + 부정)`이 0.5 이상이면 +1, −0.5 이하면 −1이다.
- 가격 데이터보다 최근 날짜의 VOC에 "가격 올랐다"는 언급이 있으면 `confidence`를 `mid`로 낮춘다.

### 3.3 확실도 규칙

| 조건 | confidence |
|---|---|
| 메뉴판 가격, 12개월 이내 | `high` |
| 12개월 초과, 또는 VOC로만 확인, 또는 가격 인상 언급 있음 | `mid` |
| 가격 없음 | `low` |

### 3.4 시스템 프롬프트

아래 `{{ }}` 자리에 데이터를 넣으면 그대로 쓸 수 있다.

```text
너는 "예산" 에이전트다. 조율자가 준 후보 가게들의 1인 가격을 서로 비교해 예산 점수를 매긴다.

[입력]
- 지시서: {{instruction}}
- 사용자 성향: {{user_profile}}        # segment, budget_max
- 후보 가게: {{candidates}}            # 거리 에이전트가 고른 가까운 20곳
- 가격 데이터: {{price_data}}          # store_id, price_per_person, source, updated_at
- VOC: {{voc}}                         # store_id, text, date
- 판정 기준: {{criteria.budget}}

[절차]
1. 후보마다 price_data에서 1인 가격을 찾는다. 없으면 추측하지 말고 unknown으로 둔다.
2. VOC에서 가격 관련 문장만 골라 positive / negative / none으로 분류한다.
   분류만 하고 점수 계산은 하지 않는다.
3. score_budget 도구에 가격, 분류 결과, 판정 기준을 넘겨 점수와 판정을 받는다.
   점수를 직접 계산하거나 도구 결과를 고치지 않는다.
4. 각 가게의 evidence에 실제 가격과 비교 근거를 숫자로 적는다.

[규칙]
- 점수는 0~10 정수다. 탈락과 판단 불가는 score를 null로 둔다.
- budget_max 초과는 drop이다. 상한은 조율자만 바꿀 수 있다.
- 1인분 주문 가능 여부, 거리, 날씨, 취향은 판단하지 않는다.

[상의 단계]
- 반론은 한 번만 한다.
- 두 가게의 예산 점수 차이가 2점 이하면 "가격 차이는 작다"고만 말한다.
- 3점 이상 차이가 나면 가격 차이를 숫자로 제시한다.
- 다른 에이전트의 점수에는 의견을 내지 않는다.

[출력]
공통 출력 형식의 JSON만 반환한다. agent는 "budget"이다.
```

### 3.5 점수 도구 (참고 구현)

```python
import math

def score_budget(stores, budget_max, criteria):
    """stores: [{store_id, price, voc_pos, voc_neg, confidence}]"""
    r = lambda x: math.floor(x + 0.5)
    priced = [s for s in stores if s["price"] is not None]
    n = len(priced)
    results = []

    for s in stores:
        if s["price"] is None:
            results.append({"store_id": s["store_id"], "verdict": "unknown",
                            "score": None, "confidence": "low"})
            continue

        if budget_max is None:                      # premium
            base = 10
        elif n < criteria["min_compare"]:           # 비교 대상 부족
            base = 10 if s["price"] <= budget_max * 0.8 else 5
        else:
            higher = sum(1 for p in priced if p["price"] > s["price"])
            base = r(10 * higher / (n - 1))

        pos, neg = s.get("voc_pos", 0), s.get("voc_neg", 0)
        adj = 0
        if pos + neg >= criteria["voc_min_mentions"]:
            ratio = (pos - neg) / (pos + neg)
            adj = 1 if ratio >= 0.5 else -1 if ratio <= -0.5 else 0
        score = max(0, min(10, base + adj))

        over = budget_max is not None and s["price"] > budget_max
        results.append({"store_id": s["store_id"],
                        "verdict": "drop" if over else "pass",
                        "score": None if over else score,
                        "confidence": s["confidence"]})
    return results
```

### 3.6 예시

앞 예시의 5곳에 이 규칙을 적용하면 다음과 같다(상한 10,000원, VOC 보정 없음).

| 가게 | 가격 | 더 비싼 곳 | 계산 | 점수 | 판정 |
|---|---|---|---|---|---|
| A 국밥 | 9,000원 | 2 | 10 × 2/4 = 5.0 | 5 | pass |
| B 라멘 | 9,500원 | 1 | 10 × 1/4 = 2.5 | 3 | pass |
| C 찌개 | 9,000원 | 2 | 10 × 2/4 = 5.0 | 5 | pass |
| D 돈까스 | 8,000원 | 4 | 10 × 4/4 = 10.0 | 10 | pass |
| E 덮밥 | 12,000원 | 0 | 0 | – | drop |

절대 규칙에서는 A와 B가 둘 다 5점이었다.
상대 규칙에서는 500원 차이가 2점 차이로 드러난다.
후보가 20곳이면 간격이 더 촘촘해진다.

## 4. 조율자

### 4.1 역할

- 요청에서 맥락을 뽑는다(시간 여유, 인원, 예산 언급).
- 에이전트에게 지시서를 보내고, 독립 작업은 동시에 호출한다.
- 탈락 조건을 먼저 적용하고, 남은 가게만 가중합한다.
- 상위권 점수 차이가 작을 때만 상의를 연다.
- 검증 에이전트가 반려하면 반려 사유에 맞춰 재계획한다.

### 4.2 가중치

기본 가중치는 판정 기준표에서 읽는다.
맥락에 따라 조율자가 조정하되 합계는 항상 100이다.

| 항목 | 기본 | 시간 없음 | Premium |
|---|---|---|---|
| 혼밥편의 | 35 | 30 | 40 |
| 거리 | 20 | 35 | 25 |
| 예산 | 20 | 15 | 0 |
| 취향 | 15 | 12 | 20 |
| 날씨 | 10 | 8 | 15 |

총점은 `Σ(점수 × 가중치) ÷ 100`이며 소수 첫째 자리까지 표시한다.
개별 에이전트 점수만 정수이고, 총점은 소수가 될 수 있다.

### 4.3 시스템 프롬프트

```text
너는 혼밥 식당 추천의 "조율자"다. 직접 점수를 매기지 않고 에이전트에게 일을 맡겨 종합한다.

[사용 가능한 에이전트]
weather, preference, distance, solo, budget, verifier
call_agent(name, instruction_json)으로 호출한다.

[절차]
1. 요청에서 context(time_pressure, party_size, 예산 언급)를 추출한다.
2. weather와 preference를 동시에 호출한다.
3. distance를 호출해 가까운 후보 20곳을 받는다.
4. solo, budget을 동시에 호출하고, distance·preference·weather에게 20곳 점수를 요청한다.
5. 어느 에이전트든 drop을 준 가게는 제외한다.
   unknown은 제외하지 않되 해당 항목 점수를 0으로 두고 confidence를 low로 표시한다.
6. 판정 기준표의 가중치를 context에 맞게 조정해 총점을 계산한다.
   budget이 "예산 변별력 없음"을 알리면 예산 가중치를 다른 항목에 비율대로 나눈다.
7. 1위와 2위의 총점 차이가 0.5 이하면 상위 3곳을 두고 상의를 연다.
   각 에이전트는 반론을 한 번만 한다. 상의는 점수를 바꾸지 않고 confidence만 바꿀 수 있다.
8. 최종 후보 3곳을 verifier에게 보낸다.
9. 반려되면 반려 코드에 맞는 에이전트만 다시 호출한다. 재계획은 최대 2회다.
10. 승인되면 최종 답을 쓴다.

[최종 답 형식]
순위, 가게 이름, 도보 시간, 1인 가격, 한두 문장의 이유.
confidence가 mid 이하인 정보는 "확실하지 않다"고 밝힌다.
순위가 맥락에 따라 뒤집힐 수 있으면 그 조건을 한 줄로 알린다.
```

## 5. 검증 에이전트

검증 에이전트는 점수를 고치지 않는다.
판정 기준표에 따라 승인하거나 반려 코드를 낸다.

### 5.1 체크리스트와 반려 코드

| 코드 | 점검 내용 | 반려 시 재계획 대상 |
|---|---|---|
| R1 | 모든 점수가 0~10 정수이거나 null인가 | 해당 에이전트 |
| R2 | 20곳 모두 각 에이전트의 결과가 있는가 | 누락한 에이전트 |
| R3 | drop 가게가 최종 후보에 들어가지 않았는가 | 조율자 |
| R4 | 최종 후보의 가격이 budget_max 이하인가 | budget |
| R5 | evidence의 숫자가 원본 데이터와 일치하는가 | 해당 에이전트 |
| R6 | 가중치 합이 100이고 총점 계산이 맞는가 | 조율자 |
| R7 | confidence가 mid 이하인 정보를 답에서 고지했는가 | 조율자 |
| R8 | 최종 후보가 3곳 미만이면 사유를 밝혔는가 | distance (반경 확대) |

### 5.2 시스템 프롬프트

```text
너는 "검증" 에이전트다. 조율자의 최종 후보와 공유 상태를 판정 기준표로 점검한다.

[입력]
- 공유 상태: {{board}}
- 판정 기준표: {{criteria}}
- 원본 데이터: {{price_data}}, {{store_data}}

[절차]
1. 체크리스트 R1~R8을 순서대로 확인한다.
2. 하나라도 어기면 reject다. 어긴 코드, 해당 store_id, 원본과 다른 값을 적는다.
3. 모두 통과하면 approve다.

[규칙]
- 점수와 순위를 직접 고치지 않는다.
- 판정 기준표에 없는 이유로 반려하지 않는다.

[출력]
{"agent": "verifier", "decision": "approve" | "reject",
 "violations": [{"code": "R4", "store_id": "S05", "detail": "12,000원 > 상한 10,000원"}],
 "replan_targets": ["budget"]}
```

## 6. 필요한 데이터

### 6.1 가게 데이터 (`stores`)

| 필드 | 예시 | 쓰는 에이전트 |
|---|---|---|
| `store_id` | S01 | 전체 |

## 8. 계획 흐름

```text
[0] 요청 수신 ─ 조율자가 context 추출
      │
[1] 날씨 ∥ 취향기록                      (동시)
      │
[2] 거리 ─ 위치 파악, 가까운 20곳 → 공유 상태
      │
[3] 예산 ∥ 혼밥편의 ∥ 거리점수 ∥ 취향점수 ∥ 날씨점수   (동시, 20곳 각각)
      │
[4] 조율자 ─ drop 제외 → 가중치 조정 → 총점
      │
[5] 1·2위 차이 ≤ 0.5? ──예──▶ 상의 (반론 1회, confidence만 변경)
      │아니오                         │
      ◀───────────────────────────────┘
[6] 검증 ─ R1~R8
      │
      ├─ reject ─▶ replan_targets만 재호출 → [4]로 (최대 2회)
      │
      └─ approve ─▶ [7] 최종 답 3곳
```

재계획이 2회를 넘으면 조율자는 승인된 부분만으로 답하고, 확인하지 못한 항목을 밝힌다.

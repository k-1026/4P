# 대구 여행객을 위한 한 끼 추천·대안 지도

> 팀 논의용 기획안 · 2026년 11월 4일
>
> 데이터 출처는 검토 후보이며, 실제 수집과 연동이 완료된 상태는 아니다.

## 1. 서비스 한 줄 소개

**먹고 싶은 음식과 여행 조건을 입력하면, 방문 가능한 식당을 비교하고 방문이 어려울 때 대안을 제시하는 지도 서비스.**

대상은 대구를 방문하는 여행객이다. 대구 10미에 한정하지 않고, 한 끼의 선택을 돕는 것부터 시작한다.

## 2. 해결하려는 문제

여행객은 맛집을 찾은 뒤에도 다음 정보를 여러 곳에서 확인해야 한다.

- 도착할 때 브레이크타임이나 마지막 주문에 걸리지 않는가?
- 혼자 또는 동행인과 주문할 수 있는가?
- 예산과 다음 일정에 맞는가?
- 리뷰에 나온 장단점이 내 상황에도 해당하는가?
- 대기가 길거나 방문이 어려우면 어디로 가야 하는가?

서비스는 **방문 조건, 리뷰의 판단 근거, 정보의 불확실성, 대안**을 함께 보여준다. 리뷰의 진위를 인증하거나 방문 가능성을 보장하는 서비스는 아니다.

## 3. 사용 예시

### 사용자 입력

> “토요일 오후 2시에 친구와 둘이 막창을 먹고 싶어요. 총예산은 4만 원이고, 오후 4시까지 동대구역에 도착해야 해요.”

음식이 정해지지 않았다면 음식 선택을 건너뛰고 위치·시간·인원부터 입력할 수 있다. 다음 일정이 있는 경우에만 목적지와 도착해야 할 시간을 추가한다.

### 지도 결과 예시

**아래 식당과 판단 결과는 기능 설명을 위한 가상 예시다.**

| 후보 | 추천 이유 | 주의점 |
|---|---|---|
| A식당 — 우선 추천 | 막창 판매, 2인 주문·예산 조건 충족. 가정한 식사시간과 이동시간을 기준으로 일정에 맞음 | 현재 대기 미확인. 대기가 길면 일정에 영향을 줄 수 있음 |
| B식당 — 같은 음식 대안 | 막창 판매, 주문·예산 조건 충족, A식당 근처 | 영업정보는 확인됐지만 현재 대기는 별도 확인 필요. A보다 덜 기다린다는 의미는 아님 |
| C식당 — 다른 음식 대안 | 사용자가 다른 음식도 허용한 경우, 찜갈비 등 다른 메뉴의 후보 제시 | 음식 종류가 달라지므로 변경되는 조건을 명시 |

각 식당에는 추천 이유, 메뉴와 주문 조건, 브레이크타임·마지막 주문, 정보의 출처·확인일을 표시한다.

## 4. 필요한 데이터와 활용 방법

| 데이터 | 주요 항목 | 확보할 곳·방법 | 서비스 활용 | 확보 시 확인할 점 |
|---|---|---|---|---|
| 식당 기본 정보 | 식당 ID, 상호, 지점명, 주소, 좌표, 음식 종류, 전화번호 | 대구 맛집 공공데이터, 카카오 또는 네이버 장소 검색 API | 지도 표시, 음식별 후보 검색, 출처별 정보 연결 | 대상 식당 포함 여부, 지점 구분, 좌표 체계 |
| 영업정보 | 요일별 영업시간, 브레이크타임, 마지막 주문, 정기·임시휴무 | 제공 데이터 확인 후 매장 공식 안내·전화 확인으로 보완 | 도착 후 주문 가능 여부 판단 | 요일·점심/저녁 차이, 임시 변경, 확인일 |
| 메뉴·주문 조건 | 메뉴명, 가격, 최소 주문량·인원, 1인 주문 여부 | 매장 메뉴판·공식 안내·직접 확인 | 음식·인원·예산 조건 확인, 예상 식사비 계산 | 가격 단위, 최소 주문 비용, 추가 주문 조건 |
| 리뷰 | 리뷰 ID, 식당 ID, 본문, 작성일, 출처, 별점이 있는 경우 별점 | 이용 가능한 데이터셋·제휴·자체 방문 후기 등 확보 경로 검토 | 혼밥·양·매운맛·서비스·대기 등의 특징 분석 | 이용 가능 범위, 표본 수, 최근성, 중복·편향 |
| 사용자 조건 | 방문 날짜·시간, 출발 위치, 이동수단, 인원, 예산, 먹고 싶은 음식, 상황·취향, 다음 일정 | 사용자가 입력 | 개인별 추천 조건 설정 | 필수 입력 최소화, 다음 일정과 취향은 필요할 때 추가 |
| 이동시간 | 출발지→식당→다음 장소의 예상 이동시간 | 경로 서비스의 제공 범위·비용 확인 후 활용 | 도착 시간과 다음 일정 충족 가능성 계산 | 장소 좌표만으로 실제 경로시간을 알 수 없음. 초기 이동수단 제한 검토 |
| 대기 관련 정보 | 대기 팀 수·시간, 확인 시각, 과거 방문 기록, 리뷰 속 대기 언급 | 매장·사용자 기록·이용 가능한 외부 정보 | 대기 주의 안내, 대기 허용시간과 비교 | 현재 현황·과거 기록·리뷰 경향을 구분 |
| 정보 확인 기록 | 정보별 출처, 수집일, 마지막 확인일, 미확인 여부 | 모든 수집 정보와 함께 관리 | 최신성과 불확실성 표시 | 서로 다른 출처의 값이 충돌하면 확인 필요로 관리 |

사용자 입력은 외부에서 수집하는 식당 데이터와 구분한다. ‘혼밥에 적합’ 등의 특징은 원본 리뷰에서 분석해 만드는 결과 데이터다.

## 5. 데이터 출처 후보와 한계

| 출처 | 활용할 부분 | 확인·보완할 부분 |
|---|---|---|
| [대구광역시 맛집 공공 API](https://www.data.go.kr/data/15057236/openapi.do) | 초기 음식점 후보 목록 구축 | 실제 제공 항목, 누락, 갱신 상태를 응답으로 확인. 대구 전체 식당을 포함한다고 가정하지 않음 |
| [카카오 로컬 API](https://developers.kakao.com/docs/latest/ko/local/dev-guide#search-by-keyword) | 상호·주소·좌표·전화번호 등 기본 정보 보완 | 장소 검색 응답에는 리뷰 본문·영업시간이 포함되어 있지 않음 |
| [네이버 지역 검색 API](https://developers.naver.com/docs/serviceapi/search/local/local.md) | 상호·주소·좌표 등 기본 정보 보완 | 지역 검색 응답에는 방문자 리뷰 본문·영업시간이 포함되어 있지 않음 |
| 매장 공식 안내·전화 확인 | 브레이크타임, 마지막 주문, 가격, 최소 주문 조건 | 직접 보완하고 확인일 기록. 계속 최신성을 유지할 방법 필요 |
| 이용 가능한 리뷰 데이터·자체 후기 | 상황별 특징과 장단점 분석 | 확보 경로와 이용 조건 검토가 선행되어야 함 |
| 경로 서비스 | 이동수단별 예상 이동시간 | 별도 서비스 선정 필요. 호출 제한·비용·저장 및 표시 조건 확인 |

세 지도에서 모든 정보를 모으는 것을 전제로 하지 않는다. 먼저 한 출처와 직접 확인으로 작은 표본을 만들고, 부족하거나 충돌하는 정보만 보완한다. API 제공 여부와 별도로 데이터의 저장·가공·표시 조건도 확인한다.

## 6. 데이터 처리와 추천 기준

### ① 식당 정보 연결·정리

- 상호뿐 아니라 주소·지점명을 확인해 같은 식당을 연결한다.
- 메뉴명, 가격 단위, 요일·시간 표기를 통일한다.
- ‘없음’과 ‘미확인’을 구분한다.

### ② 방문 조건으로 후보 분류

- 예상 도착 시각에 영업하고 주문을 받는지 확인한다.
- 인원과 최소 주문 조건을 반영해 실제 주문 비용을 계산한다.
- 다음 일정이 있으면 이동·대기·식사시간을 함께 고려한다.
- 식사시간이나 대기시간이 추정값이면 가정과 한계를 표시한다.
- 필수 정보가 부족한 후보는 조건이 확인된 후보와 구분한다.

### ③ 리뷰에서 상황별 특징 추출

- 맛, 양, 가격 만족도, 혼밥 편의, 소음, 서비스, 대기 등으로 분류한다.
- 반복되는 평가와 의견이 갈리는 항목을 구분한다.
- 분석 대상 리뷰 수와 기간을 함께 관리하고, 근거가 부족하면 판단을 유보한다.
- 작성자가 여행객인지, 아이 동반인지 등은 명시된 경우에만 활용한다.
- 리뷰 데이터 확보가 어려우면 해당 기능은 유보하고 방문 조건 기반 추천부터 진행한다.

### ④ 대안 선정

대안의 원칙은 **원래 선택한 이유를 최대한 유지하면서, 방문이 어려워진 문제를 해결하는 것**이다.

1. 시간·인원·예산 등 필수 조건 충족 여부 확인
2. 같은 음식 우선, 사용자가 허용하면 다른 음식 검토
3. 방문이 어려워진 원인이 대안에서도 반복되는지 확인
4. 추가 이동과 가격 차이 비교
5. 상황·취향 적합성으로 순서 조정

대안에는 유지되는 조건과 달라지는 조건을 함께 표시한다. 조건을 충족하는 대안이 없으면 억지로 추천하지 않고 조건 변경이 필요한 이유를 안내한다.

## 7. 대기정보 표시 원칙

| 근거 수준 | 표시 예시 | 해석 시 주의 |
|---|---|---|
| 현재 확인한 현황 | “10분 전 확인된 대기 5팀” | 사용자가 도착할 때는 달라질 수 있음. 팀 수를 곧바로 분 단위로 환산하지 않음 |
| 과거 대기 기록 | “토요일 점심 관찰 기록상 대기 20~40분” | 충분한 기록과 표본·기간 표시가 필요. 현재 대기를 뜻하지 않음 |
| 리뷰 경향 | “주말 대기 언급이 반복됨” | 현재 대기시간이나 정량 예측으로 표시하지 않음 |
| 정보 없음 | “현재 대기 확인 필요” | 대기 없음으로 처리하지 않음 |

위 문구와 수치는 표시 방식의 예시다. 실시간 대기 데이터 연동은 현재 확보되지 않았다.

## 8. 첫 버전의 범위

### 포함

- 한 구역의 식당 5곳으로 데이터 확보 가능성 검증
- 검증 후 20~30곳으로 확대 여부 결정
- 한 끼 기준 추천, 초기 이동수단 하나로 제한
- 음식·시간·인원·예산 조건 확인
- 지도에 추천 후보와 대안 표시
- 추천 이유·주의점·출처·확인일 표시
- 확보 가능한 경우에만 리뷰 분석 반영

### 이후 확장으로 유보

- 여행 전체의 끼니 배치
- 실시간 대기 예측
- 맞춤 사이드 메뉴 조합
- 알레르기 안전 판정

알레르기 정보가 확보되면 확인된 사실과 미확인 여부를 안내할 수 있지만, 리뷰에 재료가 없다는 이유로 안전하다고 판단하지 않는다.

## 9. 데이터베이스 구성 초안

| 구분 | 저장할 내용 |
|---|---|
| 식당 | 내부 식당 ID, 출처별 식당 ID, 상호·지점·주소·좌표·음식 종류 |
| 영업 일정 | 식당 ID, 적용 요일·날짜, 영업 구간, 브레이크타임, 마지막 주문, 휴무 |
| 메뉴·주문 조건 | 식당 ID, 메뉴, 가격, 최소 수량·인원 |
| 리뷰 | 리뷰 ID, 식당 ID, 본문, 작성일, 출처 |
| 분석 결과 | 식당 ID, 평가 항목, 긍정·부정·혼재 특징, 근거 리뷰, 분석 대상 기간·수 |
| 확인 기록 | 대상 정보, 출처, 수집일·확인일, 미확인·충돌 상태 |

초기에는 수집표로 검증한 뒤 데이터베이스로 옮긴다. 사용자 여행 조건은 추천 요청에 활용하며, 개인별 기록을 장기 저장하는 것은 필수 범위에 포함하지 않는다.

## 10. 프로젝트 평가

같은 여행 조건에서 ‘별점순으로 후보를 고르는 방식’과 비교한다.

- **선택 시간:** 식당을 결정하는 데 걸리는 시간
- **조건 충족:** 시간·인원·예산이 확인된 후보의 비율과 조건 위반 사례
- **선택 확신:** 추천 이유를 이해하고 선택에 확신을 느끼는 정도
- **대안 유용성:** 첫 후보 방문이 어려운 상황에서 대안을 선택할 수 있는지
- **정보 확보율:** 필수 항목 중 확인된 정보의 비율

결측 정보가 많은 결과를 조건 충족으로 계산하지 않는다. 실제 방문 검증이 없으면 ‘여행 만족도를 높였다’고 결론 내리지 않는다.

## 11. 첫 팀 회의에서 결정할 것

1. 조사할 구역과 첫 식당 5곳: 같은 음식의 비교 후보와 다른 음식 후보를 함께 선정
2. 기본·영업·메뉴 정보의 수집 담당과 공통 수집 양식
3. 리뷰 데이터 확보·이용 가능성 확인 담당
4. 이동시간 제공 방법과 초기 이동수단
